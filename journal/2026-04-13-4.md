# Session 13: Session Transaction Protocol

**Date:** 2026-04-13
**Mode:** Undirected
**Focus:** Write standalone session-transaction-protocol pattern — fault-tolerant session boundaries with dirty-close detection

## Why this

Sessions are the fundamental unit of agent team work. Every other pattern — memory, coordination, self-modification — depends on sessions opening and closing reliably. But sessions fail: context windows fill, connections drop, operators walk away mid-session. Without a transaction model, these failures leave state inconsistent.

The team-lead brief already has a concrete session protocol, and the journal-first principle was adopted in session 1 as a durability mechanism. The general pattern — applicable to any agent team — hadn't been extracted. This was next on the extraction backlog from session 8.

## What happened

Dispatched a general-purpose agent to write the pattern. The agent read the team-lead brief's session protocol (lines 36-55), plus discipline-processes.md, codification-ladder.md, and load-bearing-beliefs.md for style calibration.

**The pattern (methodology/session-transaction-protocol.md):**
- Transaction metaphor framing — sessions as database transactions, with an honest caveat that the metaphor has limits (no rollback, no isolation)
- Clean close protocol — the ordered three-step sequence (finalize journal, update memory, cross-file updates), with memory as the commit point
- Minimum viable close — pragmatic guidance for when context is running out (memory update beats polished journal)
- Journal-first as write-ahead log — the database WAL analogy, what to record mid-session (decisions, findings, state transitions, dead ends)
- Dirty close detection — four signals (pointer mismatch, incomplete journal, uncommitted changes, stale scratchpad), with a concrete example
- Reconciliation sequence — five steps including the judgment call between completing interrupted work and starting fresh
- Progressive commit — committing state incrementally after each work unit, with heuristic: commit after completing work you wouldn't want to redo
- Four anti-patterns: memory-last, journal-at-close, optimistic memory, monolithic commit
- Three design principles: idempotent opens, progressive commit over atomic commit, minimum viable close
- Evidence section: journal-first and dirty-close detection at Practised (13 sessions); full transaction model at Hypothesis; anti-patterns at Practised as observed failures
